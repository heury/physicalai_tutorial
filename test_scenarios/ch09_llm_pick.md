# 사용자 요청과 Agent 응답 요약

LLM이 도구 호출로 SO-101 로봇을 조작하는 코드를 설명하고, 카메라 관측과 정확한 좌표 제공 방식으로 각각 10회 Pick and Place를 평가한 시나리오입니다. 사용자가 요청한 대화 순서대로 정리했습니다. 테스트 실행일은 2026-10-26입니다.

관련 코드는 [`run_llm_pick.py`](../ch09/run_llm_pick.py), [`llm_agent.py`](../ch09/llm_agent.py), [`llm_client.py`](../ch09/llm_client.py), [`robot_tools.py`](../ch09/robot_tools.py)입니다.

## 1. 코드 설명

**사용자:** 이 코드 설명해

**Agent:** `ch09/run_llm_pick.py`는 LLM이 로봇 도구를 선택해 빨간 블록을 파란 상자에 넣는 프로그램이다. LLM이 다음 행동을 결정하고, MuJoCo 시뮬레이터와 기존 로봇 제어 코드가 움직임을 수행한다.

```text
실행 옵션 읽기 → LLM 클라이언트 생성 → 로봇 시뮬레이션 생성
→ LLM의 관찰·행동 반복 → 실제 좌표로 성공 판정 → 영상·기록 저장
```

### 작업과 단일 실행

```python
TASK = "Pick up the red cube and put it in the blue box."
BOX = (0.05, 0.22)
```

`TASK`는 LLM에 전달할 지시이고, `BOX`는 미터 단위의 상자 XY 좌표다. `run_once()`는 블록과 상자가 있는 `SO101Sim`을 만들고, `RobotTools`를 통해 사용할 도구를 연결한 뒤 `run_agent()`를 실행한다.

| 관측 모드 | 블록 정보를 얻는 방법 |
|---|---|
| `state` | 시뮬레이터의 정확한 좌표 제공 |
| `color` | 카메라 영상의 색 검출로 추정한 좌표 제공 |
| `camera` | `look()`으로 사진을 요청하고 LLM이 판단 |

영상 저장에는 `fixed` 카메라를, 물체 관찰에는 `top` 카메라를 사용한다. `render=True`일 때만 동작 중 영상 프레임을 수집한다.

### 성공 판정

```python
rec["success"] = bool(is_in_box(robot.cube_pos(), robot.box_pos()))
```

LLM의 성공 주장과 별도로 실제 좌표를 검사한다. 상자 중심과 블록의 X·Y 차이가 각각 5cm 미만이고, 블록 높이가 5cm 미만이면 성공이다. 기록에는 시작·최종 위치, 도구 호출 수, 종료 사유, 대화 내용 등이 포함된다.

### 실행 모드와 저장

- `--trials 1`: 지정한 위치에서 한 번 실행한다. 기본 블록 위치는 `(0.24, 0.0)`이다.
- `--trials 2` 이상: 반지름 0.17~0.27m, 각도 -0.7~0.7rad의 부채꼴 영역에서 위치를 무작위로 생성한다. 같은 `--seed`를 사용하면 같은 위치를 재현한다.
- 반복 모드에서는 `render=False`로 고정되어 영상이 저장되지 않는다.
- `--max-steps`는 LLM 응답 반복 횟수의 상한이다. 한 응답에서 여러 도구를 호출할 수도 있으므로 도구 호출 수와 개념적으로 다르다.
- 마지막에 요청 수, 입력·출력 토큰 수, API 응답 대기 시간을 출력하고 `save_trace()`로 JSON을 저장한다.

코드 자체는 `.env`를 읽지 않으므로 다음처럼 환경변수를 전달한다.

```bash
MUJOCO_GL=egl uv run --env-file .env python ch09/run_llm_pick.py \
  --out outputs/ch09_llm_pick_sample.mp4 \
  --trace outputs/traces/ch09_llm_pick_sample.json
```

앞서 수행한 기본 위치 단일 테스트는 `state` 모드에서 도구 호출 12회로 성공했다. [샘플 영상](../outputs/ch09_llm_pick_sample.mp4)은 9.7초, 640×480, 30fps이며, [실행 기록](../outputs/traces/ch09_llm_pick_sample.json)을 함께 저장했다.

## 2. LLM이 로봇을 조정하는 과정

**사용자:** llm이 로봇을 조정하는 과정을 설명해

**Agent:** LLM은 다음 행동과 목표 좌표를 결정하고, 기존 제어 코드가 이를 관절 움직임으로 변환한다. LLM이 모터를 직접 제어하지는 않는다.

```text
사용자 작업 지시 + SYSTEM_PROMPT + 도구 명세
                  ↓
           LLM이 도구 호출 선택
                  ↓
       RobotTools가 시뮬레이터에서 실행
                  ↓
         결과를 대화 기록에 추가
                  ↓
           LLM이 다음 행동 결정
```

### 작업과 관찰

`run_llm_pick.py`가 작업 지시와 로봇 사용 규칙을 전달한다. LLM은 `get_scene_state()`로 집게 위치, 개폐 상태, 상자 위치를 확인한다. `camera` 모드에서도 이 정보는 제공하며, 블록 좌표만 제공하지 않고 `look()`으로 사진을 보게 한다.

### API 요청과 도구 실행

`llm_client.py`는 전체 대화 기록과 도구 명세를 Responses API에 전달한다.

```python
r = self.client.responses.create(
    model=self.model,
    input=input_items,
    tools=tools,
)
```

LLM은 `move_gripper_to(x=0.24, y=0.0, z=0.08)` 같은 구조화된 호출을 반환한다. `llm_agent.py`는 JSON 인자를 읽고 `tools.call()`로 로컬 도구를 실행한다. API 자체가 로봇을 움직이는 것은 아니다.

| 도구 | 역할 |
|---|---|
| `get_scene_state` | 로봇과 물체 상태 확인 |
| `move_gripper_to` | 집게를 목표 좌표로 이동 |
| `set_gripper` | 집게 열기·닫기 |
| `look` | 관찰용 사진 촬영 (`camera` 모드) |
| `report_done` | 완료 또는 진행 불가 보고 |

이동 도구는 목표를 작업 범위 안으로 제한하고, 거리에 따라 이동 시간을 계산한다. 이후 `robot.move_to()`와 역기구학(IK)이 목표 관절각을 계산하고, 관절을 점진적으로 움직이며 물리 시뮬레이션을 수행한다.

### 피드백과 종료

도구는 실제 집게 위치, 목표와의 오차 등을 반환한다. 이 결과는 `function_call_output`으로 대화에 추가되며, 사진을 요청했다면 이미지도 다음 요청에 포함된다. LLM은 이 정보를 바탕으로 다음 행동이나 재시도를 선택한다.

```text
상태 확인 → 집게 열기 → 블록 위로 이동 → 내려가기
→ 집게 닫기 → 들어 올리기 → 집혔는지 확인
→ 상자로 이동 → 내려가기 → 집게 열기 → 결과 확인
```

이는 대화 중 판단을 조정하는 과정이며 모델을 학습시키는 과정은 아니다. `report_done` 호출, 도구 호출 없는 응답, 최대 스텝 도달 중 하나로 루프가 끝난다. 최종 성공은 LLM의 보고가 아니라 시뮬레이터 좌표로 판정한다.

## 3. SYSTEM_PROMPT 설명

**사용자:** SYSTEM_PROMPT 설명해

**Agent:** `robot_tools.py`의 `SYSTEM_PROMPT`는 로봇 특성과 조작 방법을 알려주는 작업 지침이다. 작업 목표와 함께 전달되어 LLM의 도구·좌표 선택 기준이 된다.

### 로봇과 좌표계

5자유도 SO-101 로봇을 MuJoCo에서 조작하며, 로봇 밑동이 원점인 월드 좌표계와 미터 단위를 사용한다고 설명한다. 집게는 위에서 아래로 접근하도록 안내한다.

### 집기·놓기 높이

블록은 한 변이 3cm이고 바닥에 놓인 중심 높이는 1.5cm다. 너무 높은 곳에서 집게를 닫으면 잡지 못하고, 너무 낮으면 바닥과 충돌한다고 설명한다.

| 단계 | 목표 높이 | 목적 |
|---|---:|---|
| 접근 | `z=0.08` | 블록 위로 이동 |
| 집기 | `z=0.02` | 손가락으로 블록 옆면 잡기 |
| 들어 올리기 | `z=0.12` | 옆으로 이동할 때 바닥에 끌리지 않도록 하기 |
| 놓기 | `z≈0.06` | 상자 위에서 집게 열기 |

이 지침은 LLM이 조작 방법을 처음부터 추측하지 않도록 기존 동작 지식을 제공한다.

### 작업 범위와 이동 결과 해석

수평 거리가 원점에서 12~30cm인 목표를 사용하도록 안내하며, 범위 밖 좌표는 실제 `clamp_target()` 코드에서 제한한다. 범위 안에서도 관절 구조와 집게 방향 때문에 목표에 정확히 도달하지 못할 수 있다.

- `position_error`: 요청한 위치와 실제 집게 위치의 거리다. 프롬프트에서는 2cm 미만을 허용할 만한 수준으로 안내한다.
- `tilted`: 수직 자세 유지가 어려웠다는 신호로 설명하며, 이것만으로 집기 실패를 판단하지 않도록 한다. 실제 구현은 기울기를 직접 측정하지 않고 IK 잔차가 큰지 확인하는 대리 지표라 위치 오차 때문에 켜질 수도 있다.
- 실제 도착한 좌표를 새 목표로 그대로 재전송하지 않도록 한다. 반복 이동이 자세를 더 어긋나게 할 수 있어 다른 목표를 선택하거나 작업을 계속하도록 안내한다.

### 집기 확인과 종료

`get_scene_state()`로 블록의 Z값을 읽어 바닥 높이보다 충분히 올라갔는지 확인하고, 완료했거나 진행할 수 없으면 `report_done`을 호출하도록 한다.

다만 `camera` 모드는 `get_scene_state()`에서 블록 좌표를 제공하지 않는다. 따라서 Z값으로 확인하라는 공통 지침은 이 모드와 맞지 않으며, 사진으로 확인하도록 별도 지침을 주는 편이 일관된다. 이 대화에서는 이 점을 설명했으며 프롬프트를 수정하지는 않았다.

프롬프트는 판단을 유도하는 설명이고, 실제 좌표 제한·속도·관절 제어·최종 판정은 Python 코드가 수행한다.

## 4. 카메라를 이용한 10회 테스트

**사용자:** 카메라를 이용해서 10회 테스트 진행해

**Agent:** 사진으로 블록을 판단하는 `camera` 모드로 무작위 위치 10회를 실행했다. 색 검출 좌표를 제공하는 `color` 모드와 구분했다.

```bash
MUJOCO_GL=egl PYTHONUNBUFFERED=1 uv run --no-sync --env-file .env \
  python ch09/run_llm_pick.py \
  --perception camera --trials 10 --seed 0 --no-video --verbose \
  --trace outputs/traces/ch09_llm_pick_camera_10.json \
  > outputs/logs/ch09_llm_pick_camera_10.log 2>&1
```

모델은 `gpt-6-astra`, 회차당 최대 스텝은 기본값 25였다. 관찰용 카메라는 사용하지만 반복 실행 영상은 저장하지 않았다. 위 명령의 로그 디렉터리는 실행 전에 준비되어 있었다.

**결과: 7/10 성공, 성공률 70%.**

- 성공: 3·4·5·6·7·8·9회차.
- 실패: 1·2·10회차.
- 6·7·9회차는 스텝 상한으로 종료됐지만 실제 블록이 상자 안에 있어 성공으로 판정했다.
- LLM 요청 205회, 입력 368,060토큰, 출력 8,328토큰, 총 376,388토큰이었다.
- API 응답 대기 합계는 약 611초이며, 에피소드당 평균 요청 20.5회였다.

## 5. 카메라 없이 10회 테스트하고 결과 비교

**사용자:** 카메라 없이 10회 테스트 진행해서 결과 비교해

**Agent:** 시뮬레이터의 정확한 좌표를 제공하는 `state` 모드로 10회 실행했다. 같은 모델, `seed=0`, 최대 25스텝을 사용했고, 두 기록의 시작 위치 10쌍이 일치하는지 확인했다.

```bash
MUJOCO_GL=egl PYTHONUNBUFFERED=1 uv run --no-sync --env-file .env \
  python ch09/run_llm_pick.py \
  --perception state --trials 10 --seed 0 --no-video --verbose \
  --trace outputs/traces/ch09_llm_pick_state_10.json \
  > outputs/logs/ch09_llm_pick_state_10.log 2>&1
```

**결과: 9/10 성공, 성공률 90%. 카메라 모드보다 20%p 높았다.**

| 항목 | 카메라 `camera` | 좌표 제공 `state` |
|---|---:|---:|
| 성공 | 7/10 (70%) | 9/10 (90%) |
| LLM 요청 | 205회 | 123회 |
| 입력 토큰 | 368,060 | 129,993 |
| 출력 토큰 | 8,328 | 3,468 |
| 총 토큰 | 376,388 | 133,461 |
| API 응답 대기 합계 | 약 611초 | 약 256초 |

`state` 모드는 요청 수가 40%, 총 토큰이 약 65%, API 응답 대기 시간이 약 58% 줄었다. 대기 시간은 전체 프로그램 실행 시간이 아니라 API 응답을 기다린 시간의 합계다.

1·10회차는 카메라에서 실패했지만 좌표 제공 시 성공했다. 2회차는 두 방식 모두 실패했으며, `state`에서도 집은 뒤 이동 오차가 커져 상자까지 옮기지 못했다. 나머지 7회차는 모두 성공했다. `state`의 성공 회차는 전부 도구 호출 12회로 종료됐다.
